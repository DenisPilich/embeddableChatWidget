# Embeddable Chat Widget — план проекта

**Статус:** план согласован, код не начат.
**Связанные документы:** [DECISIONS.md](./DECISIONS.md) — журнал принятых решений (он же основа раздела «решения» в портфолио-кейсе).

---

## 1. Что это за проект

Встраиваемый чат-виджет: владелец сайта вставляет одну строку `<script>` на свою страницу и получает окно чата, в котором **по умолчанию отвечает LLM**, а живой оператор подключается только когда нужен.

**Двойная цель:**

1. **Продукт для демонстрации.** Демо должно впечатлять за 15 секунд: кликнул → виджет открылся → AI ответил. Без регистрации, без «оператор offline».
2. **Доказательство инженерных навыков.** Главная техническая суть проекта — не AI (его сейчас умеют все), а то, что **сторонний код живёт на чужой странице и не ломает её**: изоляция через Shadow DOM, бандл в единицы килобайт, устойчивость к враждебной вёрстке и строгой CSP, автоматическая деградация при отказе realtime.

**Честный ответ на вопрос «зачем, если есть Chatwoot/Crisp/Tidio»:** я не делаю замену им. Я делаю проверяемое доказательство, что умею: изоляцию стороннего скрипта на чужом сайте, multi-tenant SaaS с разграничением данных, realtime с fallback, стриминг LLM с контролем расхода и воспроизводимый релизный процесс. Этот ответ обязателен в README.

## 2. Стек и почему именно он

| Слой | Выбор | Почему |
|---|---|---|
| Виджет | Vanilla TypeScript + Vite (library mode) | Нужен минимальный вес и полный контроль над изоляцией. Фреймворк здесь — лишний вес и лишний слой стилей |
| Стили виджета | Обычный CSS внутри Shadow DOM | ~200 строк CSS; Tailwind добавляет билд-слой, который не окупается |
| Дашборд + API | Next.js (App Router) + TypeScript | Совпадает с уже знакомым стеком портфолио; один деплой на Vercel |
| UI дашборда | Tailwind + shadcn/ui | Polaris — дизайн-система Shopify Admin, для не-Shopify проекта это чужеродный выбор |
| БД | Neon (Postgres) + Prisma | Бесплатный тариф, привычный ORM, branching для preview-окружений |
| Realtime | Поллинг → SSE → (Ably или Durable Objects, решение в Фазе 4) | См. [ADR-002](./DECISIONS.md#adr-002-транспорт-поллинг--sse-выбор-push-слоя-отложен) |
| LLM | Groq, за интерфейсом провайдера | Быстрый стриминг, есть бесплатный тариф без карты. Жёсткие лимиты обязательны |
| Структура | Монорепо, pnpm workspaces | Общий контракт API между виджетом и бэкендом, одна правка вместо двух |
| Распространение виджета | npm publish → jsDelivr, **версия в URL обязательна** | См. [ADR-006](./DECISIONS.md#adr-006-распространение-виджета--npm--jsdelivr-с-версией-в-url) |

## 3. Структура репозитория

```
packages/widget      — то, что встраивают на сайт (собирается в один файл, публикуется в npm)
packages/shared      — типы и контракт API, используются и виджетом, и бэкендом
apps/web             — лендинг + дашборд агента + API (один Next.js на Vercel)
apps/fixtures        — «чужие сайты» для разработки и E2E-тестов
docs/                — план, решения, кейс
```

`apps/fixtures` — не второстепенная папка. Это твой основной инструмент разработки: без локального «чужого сайта» каждая проверка одной строки CSS превращается в деплой.

## 4. Фазы

Каждая фаза заканчивается **критерием выхода** — конкретной проверкой, а не ощущением «вроде готово». Ни одна фаза не оставляет проект в нерабочем состоянии: после Фазы 1 уже есть что показать, после Фазы 2 уже работает продукт.

### Фаза 0 — Фундамент

**Состояние: завершена.**

| Шаг | Что делаем | Состояние |
|---|---|---|
| 0.1 | Решения зафиксированы в [DECISIONS.md](./DECISIONS.md) | готово |
| 0.2 | `git init`, монорепо на pnpm workspaces, общий tsconfig | готово |
| 0.3 | Локальный стенд: dev-сервер отдаёт fixture-страницу | готово |
| 0.4 | Факты о рабочей среде записаны (раздел 7) | готово |

**Что узнаёшь:** pnpm workspaces, структура библиотечного пакета, конфигурация TypeScript для нескольких пакетов, разница между сборкой приложения и сборкой библиотеки.
**Критерий выхода:** `pnpm dev` открывает fixture-страницу; `pnpm build` собирает виджет; `pnpm typecheck` проходит; история git есть. — выполнено.

Что получилось:

- монорепо из четырёх пакетов, зависимости между пакетами объявляются явно (`@ecw/shared` как `workspace:*`) — неявных связей нет;
- виджет собирается в двух форматах: ES для тех, кто ставит пакет из npm, и IIFE для вставки через `<script>`;
- стенд отдаёт собранный виджет по адресу `/ecw-widget.iife.js` — ровно тем способом, каким его получит клиент с CDN, без импортов из монорепо;
- страница стенда намеренно «чужая»: собственные стили и шрифт с засечками. Это приманка: если в Фазе 1 текст внутри виджета окажется с засечками, значит сброс стилей на `:host` сделан неправильно;
- общий пакет `@ecw/shared` намеренно собран без доступа к DOM — ошибка «использовал `document` в общем коде» должна ловиться компилятором, а не в рантайме.

### Фаза 1 — Виджет с мок-бэкендом (без сервера вообще)

**Состояние: завершена, кроме публикации пакета.**

- Готово: 1.0 (линтер и форматтер), 1.1 полностью (host в нужном узле, Shadow DOM, окно, загрузчик с ленивой загрузкой), 1.2 (лента сообщений, поле ввода, отправка, ответ-заглушка, индикатор набора, автопрокрутка, мобильный полный экран), 1.3 (история переписки в хранилище посетителя и счётчик непрочитанных), 1.5 (удержание фокуса, Esc, возврат фокуса, доступная с клавиатуры прокрутка переписки, live-регион), 1.6 (бюджет размера и перенос стилей в CSS-файл), 1.8 (41 автотест на пяти стендах).
- Из 1.4 сделано: host в `document.body` с переносом в `<html>` при трансформированном body, сброс наследуемых свойств на внутренней обёртке, `z-index`, весь код в try/catch.
- Враждебный стенд нашёл настоящий дефект изоляции — см. ADR-010. Это единственный дефект в проекте, найденный не рассуждением, а проверкой.
- Перенос стилей из JS-строки в CSS-файл сократил бандл с 8.89 до 6.71 КБ gzip, загрузчик добавил ещё 592 байта. Подробности — в ADR-011 и ADR-012.
- 1.7 подготовлен: пакет назван `ecw-widget` (имя в реестре свободно; область `@ecw` нам не принадлежит, а публиковать в чужую нельзя), состав архива выверен через `npm pack`, объявления типов собираются, зависимостей времени выполнения нет. Осталось запустить `npm publish` со своего аккаунта.
- Бандл на текущий момент: 7.48 КБ gzip при бюджете 15 КБ и 592 байта при бюджете 2 КБ. Превышение бюджета ломает `pnpm verify`.

| Шаг | Что делаем |
|---|---|
| 1.0 | Линтер и форматтер на весь монорепо — перенесено из Фазы 0: правила для браузерного кода полезнее настраивать, когда есть код, на котором они срабатывают |
| 1.1 | Каркас: entry-точка, защита от двойной инициализации, загрузчик + ленивая загрузка основного бандла |
| 1.2 | UI: кнопка-лаунчер, окно, шапка, лента сообщений, поле ввода, мобильный полный экран |
| 1.3 | UX-логика: отправка, ответ-заглушка, индикатор «печатает…», история в localStorage, счётчик непрочитанных, автопрокрутка |
| 1.4 | Изоляция: host-элемент в `document.body`, сброс наследуемых свойств на `:host`, z-index, весь код в try/catch, события с `composed: true`, обработка недоступного localStorage |
| 1.5 | Доступность: работа с клавиатуры, Esc, ловушка фокуса, `aria-live` для новых сообщений, `prefers-reduced-motion` |
| 1.6 | Бюджет размера в CI: загрузчик ≤ 2 КБ gzip, основной бандл ≤ 15 КБ gzip |
| 1.7 | Публикация в npm → проверка установки через jsDelivr с версией в URL |
| 1.8 | Fixture-матрица: чистая HTML, «враждебная» страница, WordPress-подобная (jQuery), SPA (React StrictMode + роутинг), страница со строгой CSP |

**Что узнаёшь:** Shadow DOM по-настоящему (наследование CSS, границы изоляции), сборка библиотеки, ленивая загрузка, immutable-версионирование published-контракта, E2E-тесты, доступность.
**Критерий выхода:** виджет работает на всех пяти стендах, не ломает чужую страницу, укладывается в бюджет, подключается одной CDN-ссылкой с версией. **На этом этапе проект уже можно показывать людям.**

### Фаза 2 — Бэкенд и рабочий чат по HTTP

**Состояние: начата.**

- Каркас `apps/web` поднят: Next.js 16, проверка работоспособности на `/api/health`, сборка проходит.
- Схема данных написана: `User, Workspace, Membership, Site, Visitor, Conversation, Message, AiConfig, TokenUsage`. Миграции ждут базы — без настоящего подключения их не применить.
- `WidgetSession` из первоначальной схемы убран: сессия посетителя живёт в подписанном токене, а не в таблице. Сущность `Visitor` заменяет её и решает больше задач.
- Обнаружено при работе: **Prisma 7 убрала строки подключения из схемы.** Адрес для миграций теперь в `prisma.config.ts`, а клиент в рантайме требует адаптер драйвера. См. ADR-013.
- Обнаружено: **в pnpm 11 настройка `onlyBuiltDependencies` удалена**, вместо неё `allowBuilds`. Из-за этого сборочные скрипты Prisma молча не запускались.

| Шаг | Что делаем |
|---|---|
| 2.1 | Схема Prisma + миграции |
| 2.2 | `POST /init`: проверка `Origin` по `Site.allowedOrigins`, rate limit, Turnstile, выдача подписанного токена (`siteId`, `visitorId`, `conversationId`, срок жизни) |
| 2.3 | API чата: отправка с идемпотентностью по `clientId`; выборка новых по курсору `after=seq` |
| 2.4 | Виджет: `PollingTransport` за интерфейсом `Transport` |
| 2.5 | Изоляция тенантов: repository-слой с обязательным `siteId` + тест на утечку между сайтами |
| 2.6 | Санитизация текста, лимиты длины сообщений |

**Что узнаёшь:** multi-tenancy и почему одна забытая проверка `siteId` = утечка чужой переписки, подписанные токены, Prisma + Neon в serverless (pooled и direct URL, только Node-рантайм, `prisma generate` в сборке), ограничения бесплатных тарифов.
**Критерий выхода:** сообщение с чужой страницы доходит до базы и возвращается в виджет; запрос с постороннего Origin отклонён; тест на утечку зелёный. **На этом этапе это уже работающий продукт.**

### Фаза 3 — AI и передача оператору

| Шаг | Что делаем |
|---|---|
| 3.1 | Провайдер LLM за интерфейсом, системный промпт на уровне сайта, стриминг через SSE |
| 3.2 | Виджет: приём потока, индикатор печати, отмена генерации |
| 3.3 | Правила передачи человеку: просьба о человеке, N неудачных ответов, тема вне области, кнопка «позвать оператора» |
| 3.4 | Защита: дневной бюджет токенов на сайт, лимит на диалог, таймаут, запрет попадания в контекст системного промпта и чужих данных |

**Что узнаёшь:** потоковая передача, prompt injection, управление стоимостью LLM.
**Критерий выхода:** AI отвечает потоком; при исчерпании бюджета виджет честно деградирует, а не падает; попытка выманить системный промпт не срабатывает.

### Фаза 4 — Realtime

| Шаг | Что делаем |
|---|---|
| 4.1 | SSE-канал подписки + переподключение с `Last-Event-ID`, уведомления о новых сообщениях |
| 4.2 | Логика деградации: SSE недоступен → поллинг; реакция на видимость вкладки |
| 4.3 | Решение Ably против Durable Objects по критериям ниже |
| 4.4 | Presence («печатает…» со стороны оператора), если выбран push-слой |

**Критерий выбора push-слоя:**

- **Ably** — если время дороже вендорской зависимости. ~50 строк кода, каналы и токены с правами на один диалог.
- **Durable Objects (через «Путь A»)** — если важнее пункт «realtime-слой построил сам». Worker с DO только для широковещания, при этом Vercel + Neon + Prisma не трогаются. Цена: +4–8 дней и второй пайплайн.

Решение обратимо, потому что транспорт спрятан за интерфейсом `Transport`, а поллинг уже написан.

**Критерий выхода:** новые сообщения приходят с задержкой меньше секунды; при обрыве соединения виджет молча возвращается на поллинг, и переключение видно в логах.

### Фаза 5 — Дашборд агента

Вход через GitHub OAuth, список диалогов, окно переписки, статусы open/closed, назначение оператора, настройки внешнего вида виджета (цвет, позиция, приветствие), «проверка установки» (зелёная галочка после вставки сниппета).

**Что узнаёшь:** realtime-состояние на клиенте, санитизация пользовательского текста (XSS в интерфейсе агента — реальная угроза).
**Критерий выхода:** оператор видит новое сообщение без перезагрузки и отвечает; изменения настроек видны на чужой странице.

### Фаза 6 — Онбординг и метрики

Регистрация → создание сайта → получение `siteId` → готовый сниппет для копирования → подтверждение установки. Плюс две метрики: количество диалогов за неделю и среднее время до первого ответа.

**Критерий выхода:** человек без подсказок извне проходит путь от регистрации до работающего виджета на своём сайте.

### Фаза 7 — CI/CD, деплой, домен

GitHub Actions: typecheck, lint, тесты, сборка, проверка размера бандла. Изменения версий через changesets. Публикация по тегу с подтверждением происхождения сборки. Миграции БД — только на `main`. Preview-деплои с ветками Neon. Фиксированный домен для OAuth-callback и realtime.

**Что узнаёшь:** релизный процесс библиотеки, безопасная доставка миграций, preview-окружения.
**Критерий выхода:** тег → пакет в npm и на CDN; PR → preview; `main` → прод с применёнными миграциями.

### Фаза 8 — Кейс и проверка на реальных сайтах

Внедрение на 3+ реально чужих сайта (чистая HTML, WordPress, React). Лендинг проекта с живым демо. README с GIF «как встроить за 30 секунд». Пост-разбор: что было сложно, какие решения принял, что не сработало.

**Критерий выхода:** работающее живое демо, кейс с реальными решениями и сложностями, ссылки на внедрения.

## 5. Чего НЕ делаем (сознательно)

Список существует, чтобы через месяц не начать «а давай ещё». Каждый пункт — осознанный отказ, а не забывчивость.

| Не делаем | Почему |
|---|---|
| Вложения и файлы | Нужно объектное хранилище, лимиты, модерация. Объём не оправдан для портфолио |
| Регистрация по email/паролю | GitHub OAuth бесплатен и не требует почтовой инфраструктуры и писем-подтверждений |
| Polaris | Дизайн-система Shopify Admin; в не-Shopify проекте выглядит случайным выбором |
| Отдельная фаза метрик | Две цифры на дашборде вместо аналитической подсистемы |
| Отдельная фаза анимаций | 30 строк CSS-переходов, а не задача |
| Полноценная i18n | Только если останется время; не влияет на суть проекта |
| Мобильные приложения, голос, видео | Вне области задачи |

## 6. Риски и что с ними делать

| Риск | Почему реален | Митигация |
|---|---|---|
| Бесплатные тарифы меняются, демо ломается | Квоты и условия вендоров меняются без предупреждения | Проектировать деградацию: realtime → поллинг, LLM-бюджет исчерпан → честное сообщение. Демо не должно ломаться целиком |
| Публичное демо выжигает лимит LLM | Один скрипт с циклом = мёртвая квота | Дневной бюджет токенов, лимит на диалог, Turnstile, rate limit |
| Объём работ больше ожидаемого | Проект впервые, 80–130 часов | Вертикальные срезы: каждая фаза даёт работающий результат, а не половину слоя |
| Проект брошен на 60% | Классический исход больших пет-проектов | После Фазы 1 есть демо, после Фазы 2 есть продукт. Даже остановка даёт результат |
| Расход квоты Neon из-за поллинга | Опрос держит базу активной, 100 CU-hours ≈ 400 часов бодрствования в месяц | Адаптивный интервал, остановка опроса в скрытой вкладке, опрос только открытого диалога |
| Durable Objects съедают время | Незнакомая платформа вместо знакомого Node | Решение отложено до Фазы 4 и обратимо |
| Утечка данных между тенантами | Одна забытая проверка `siteId` | Repository-слой с обязательным `siteId` + тест на утечку |
| Prompt injection | Публичный чат с LLM | Никаких чужих данных в контексте, лимиты, проверка на попытки выманить промпт |

| PowerShell и `.ps1` | Выполнение скриптов запрещено политикой системы; из песочницы политику изменить нельзя | Вызывать `npm.cmd` и `pnpm.cmd`. В своём терминале разрешается командой `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` |
| Блокировка хранилища pnpm | Лежит в `%LOCALAPPDATA%\pnpm-store-operation-locks`, вне папки проекта | В песочнице любые операции с пакетами требуют полного доступа: запускать их пачками, а не по одной |
| Любая команда Vite (`build` и `dev`) | При загрузке конфигурации запускает вспомогательный процесс с перехватом вывода, что песочница запрещает (`spawn EPERM`) | В песочнице требует полного доступа; в обычном терминале ограничений нет. `typecheck`, `lint` и `format` работают без него |
